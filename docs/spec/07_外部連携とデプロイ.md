# 07 外部連携とデプロイ

## 1. employee-manager（社員情報管理プラグイン）

| 項目 | 内容 |
|---|---|
| 役割 | 社員マスタの提供元。本プラグインは社員情報を**保持せず**、都度ここから取得する |
| 連携方式 | `PL_Employee_Bridge` が公開関数を `function_exists` で確認して呼ぶ |
| 使う関数 | `emp_get_active_employees($args)`、`emp_get_employee_by_code($code)`、`emp_get_employee_by_id($id)`、`emp_get_affiliations()`、`emp_get_departments()` |
| 取得項目 | `employee_code`, `name`, `hire_date`, `employment_type`, `weekly_work_days`（`$args` で `affiliation_id` / `department_id` による絞り込みが可能） |
| 無効時の挙動 | 空配列／null を返す（エラーにはしない）。結果として一覧は空、検索は「社員が見つかりません」になる |
| 例外 | 申請一覧（`PL_Request::get_list`）のみ `{prefix}emp_master` テーブルを直接 JOIN して `name` を取得 |
| 未登録時の既定 | 週勤務日数が空なら **5日** として扱う（付与判定・CSV取込） |

> employee-manager 側の仕様（テーブル構造・在籍判定ロジック・週勤務日数の取りうる値）はこのリポジトリに無いため、本資料の範囲外。「在籍中」の定義は `emp_get_active_employees` に依存する。

## 2. MAT（勤怠アプリ）連携

- **方向**：MAT → 本プラグイン（一方向）。MAT が有給希望を保存すると WordPress アクション `my_attendance_paid_leave_saved` を発火し、配列ペイロードを1つ渡す。
- **受け口**：`PL_Mat_Bridge::on_paid_leave_saved`（`new PL_Mat_Bridge()` をプラグイン読込時に常時生成）。
- **処理**：`employee_code`・`paid_leave_date` が揃っていれば `PL_Request::create` で `pending` の申請を作成（休日・重複は作られない）。
- **逆方向（承認結果の通知）**：コード上は無い。MAT 側が `pl_get_request_status($employee_code, $date)` を呼んで状態を確認する想定の関数が公開されているが、内部で呼ぶ `PL_Request::get_status` が未実装（09 参照）。
- **ペイロード項目**：`emp_master_id`, `employee_code`, `employee_name`, `paid_leave_date`, `log_id`, `action`（insert/update）。

## 3. 内閣府 祝日CSV

| 項目 | 内容 |
|---|---|
| URL | `https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv` |
| 取得 | `wp_remote_get`（タイムアウト30秒） |
| 文字コード | Shift-JIS → UTF-8（`mb_convert_encoding`。mbstring 拡張が必要） |
| 形式 | 1行目ヘッダー、以降 `YYYY/M/D,祝日名`。2列目までを使用 |
| 保存 | 祝日テーブルへ upsert（日付がキー） |
| 自動更新 | 毎年4月1日 0:00（サーバー時刻）に WP-Cron イベント `pl_annual_holiday_fetch`。有効化時／毎回の読込時に未登録なら登録 |
| 手動更新 | 有給ルール設定 →「内閣府CSVから祝日を取得・更新」 |
| オンデマンド取得 | 休日判定で、該当年のデータがテーブルに無い場合に自動取得（失敗しても処理は続行） |
| 失敗時 | `error_log('[PL_Holiday] fetch failed: …')` を出力して false を返す |

## 4. WP-Cron
- イベント：`pl_annual_holiday_fetch`、周期名 `yearly`。
- 無効化（deactivate）時に `wp_clear_scheduled_hook` で解除。
- WordPress 標準には `yearly` という周期は無い（hourly / twicedaily / daily / weekly のみ）。`cron_schedules` フィルタで定義するコードはこのプラグイン内に見当たらない。したがって**自動更新が実際に動作しているかは要確認**（09 参照）。年次データは上記のオンデマンド取得と手動更新で補える。

## 5. デプロイ（GitHub Actions → FTP）

使用アクション：`SamKirkland/FTP-Deploy-Action`（v4.3.0 / v4.3.4）。FTP 認証情報は GitHub Secrets。

| ワークフロー | トリガー | 配置先（FTPサーバー内パス） | Secrets |
|---|---|---|---|
| `deploy.yml`（Deploy to XSERVER） | `main` ブランチへの push | `/xs969605.xsrv.jp/public_html/inhouse/wp-content/plugins/paid-leave-manager/`（本番） | `FTP_HOST_TANPOPO` / `FTP_USER_TANPOPO` / `FTP_PASS_TANPOPO` |
| `staging-deploy.yml` | `staging` ブランチへの push | `/labs-ims.com/public_html/tanpoposub-test.labs-ims.com/wp-content/plugins/paid-leave-manager/` | `FTP_HOST_STAGING` / `…_USER_STAGING` / `…_PASS_STAGING` |
| `personal-deploy.yml` | `feature/shiroto*` ブランチへの push | `/labs-ims.com/public_html/shiroto-test/tanpop/wp-content/plugins/paid-leave-manager/`（個人検証、`dangerous-clean-slate: false`） | `FTP_HOST_SHIROTO` 等 |

- ブランチ運用（履歴より）：機能ブランチ `feature/…` → PR → `staging` → PR → `main`。
- リポジトリ全体（`local-dir: ./`）が配備対象。ビルド工程・自動テストは無い。`.git` などは Action が既定で除外。
- 注意：本 `docs/` フォルダや `test.html` も、除外設定が無いためそのままサーバーに配置される。公開が望ましくない場合は `exclude` 設定を追加すること。

## 6. 運用上の前提
- PHP 拡張：`mbstring`（祝日CSVの文字コード変換）。
- WordPress の管理画面・`admin-ajax.php` が利用可能であること。
- サーバーのタイムゾーンが日本時間であること（`date()` を多用。日付境界がずれると失効・「今日」の判定に影響）。WordPress 側の時刻（`current_time`）は更新日時の記録にのみ使用。
- 大量データ（CSV 数万行）：付与インポートは全既存キーをメモリに読み込む実装。アップロード上限は30MB。
