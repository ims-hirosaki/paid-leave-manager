# 09 既知の課題と実装差異

ソースコードの読解から確認できた、README との差異・未使用の設定・潜在的な不具合や運用上の注意点です。
重要度：**高**＝データ不整合・業務影響の可能性／**中**＝想定と異なる動作／**低**＝軽微・保守性。
「確認方法」欄は根拠のコード箇所です。修正の要否は運用判断によります（本資料は事実の記録であり、修正は行っていません）。

## 2. 重要度「高」

**H1. アンインストール時に未定義メソッドを呼ぶ**
`uninstall.php` が `PL_DB_Install::drop_tables()` を呼ぶが、`class-db-install.php` に定義がない。プラグイン削除時に致命的エラーとなり、テーブルは削除されない（意図した「削除でDROP」は動かない）。

**H2. 付与の二重登録を防ぐチェックが無い**
`PL_Grant::execute_grant` に「同社員・同付与日（同区分）の重複」チェックが無い。画面の付与ボタンも「付与済み」かどうかを判定せず、毎回付与可能と表示する（勤続月数は到達済み最大区分で判定されるだけ）。CSV取込のみ「社員番号＋付与日」で重複判定する。誤って二重に付与すると取り消し手段が無い。

**H3. 誤登録の取消・修正機能が無い**
付与・消化ログの削除／修正機能は無い（READMEも今後の拡張に記載）。唯一の削除手段は「テストデータ削除」で、社員単位または全件の物理削除のみ。

**H4. 週5勤務の社員の付与ルールが初期状態では引けない**
初期データは週6列にフルタイム値が入り、週5列は存在しない。週5の社員は「ルールが見つかりません」、ルール設定を一度保存すると週5列が0日で保存され「0日付与」で付与不可になる（03）。employee-manager 側で週勤務日数が「5」で保存されている社員が多い場合、運用開始時に必ず対処が必要。

**H5. 申請受理が「受理済み」を先に確定する**
`PL_Request::approve` は状態を `approved` にしてから消化登録を実行する。消化登録に失敗しても `approved` のままで、再度の受理はできない（「すでに受理済み」）。また受理時は休日・同日重複・残日数の事前チェック（`check_consumable`）を行わないため、既に同日の消化がある場合は**二重に消化が登録され得る**。失敗時は手動登録の案内メッセージのみ。

**H6. `remaining_days`（付与テーブル）と消化ログの二重管理**
残日数は付与レコードの列と消化ログの両方で表現され、整合性を保証する仕組み（トランザクション・再計算バッチ）が無い。複数付与にまたがる消化の途中で失敗しても、先に書いた分はロールバックされない（`PL_Consumption::execute`）。CSV消化インポートで失効済み付与に充当した場合は残日数据え置きの仕様のため、集計の「付与−消化＝残」は一致しない。

## 3. 重要度「中」

**M1. 保存されるだけで使われない設定**
`carryover_years`（繰り越し年数）、`min_annual_days`（年間最低取得日数）、`default_consumption_unit` は保存されるが、計算では参照されない。繰り越しは実質「有効期限（`expiration_years`）」で表現されている。管理者が値を変えても動作は変わらないため、利用者に誤解を与える。

**M2. 祝日の年次自動更新が動作しない可能性**
`wp_schedule_event(…, 'yearly', …)` の周期 `yearly` は WordPress 標準に無く、`cron_schedules` での追加定義も無い。登録に失敗していると、毎回の読込で再試行され続け、自動更新は行われない。休日判定は、その年のデータが無いと自動取得するため業務上は致命的ではないが、手動更新が必要。

**M3. 休日判定のたびに外部取得が走り得る**
指定年の祝日が0件のとき（取得失敗・祝日が無い遠い将来年）、`is_holiday` の呼び出しごとに内閣府へアクセスする。期間一括消化や CSV 取込以外でも、将来日付の消化・申請が遅くなる可能性がある。

**M4. 従業員一覧の「在籍中／全員／退職者」切替が無効**
セレクトはあるが JS で参照されず、常に `emp_get_active_employees()` の結果（在籍中）のみ表示。

**M5. 集計表の消化率が100%を超え得る／画面ごとに消化率の分母が違う**
03 参照。付与ベースは「期間内の消化」÷「期間内の付与」。個人管理（有効期間）と付与・消化登録（全期間・失効含む）でも定義が異なる。

**M6. `pl_get_request_status()` が未実装メソッドを呼ぶ**
グローバル関数が `PL_Request::get_status` を呼ぶが定義が無い。MAT 側がこの関数を呼ぶと致命的エラーになる。

**M7. MAT連携の取りこぼし**
`PL_Mat_Bridge` は `PL_Request::create` の戻り値（WP_Error）を確認しない。休日・重複・DBエラー時は黙って無視され、MAT側にも通知されない。`action=update`（希望日の変更）にも対応せず、旧日付の申請は残る。

**M8. 消化インポートは休日・重複単位のチェックが緩い**
CSV 消化は「社員番号＋消化日」の重複のみ判定。休日（日曜・祝日）や1日に満たない既存消化の有無は確認しない。画面登録とルールが異なる。

**M9. 付与登録は日数・日付の妥当性をサーバー側で検証しない**
`pl_grant_execute` は日数が0より大きいことのみ確認。ルールと異なる日数、未来日付、入社日より前の付与日も登録できる。

**M10. 申請管理ページ（`pl-requests`）の JS が二重・不整合**
`admin.js` の `#pl-requests-page` ブロックは存在しない AJAX（`pl_requests_get`、`pl_request_update`）を呼ぶ旧実装。有効化（`PL_SHOW_REQUESTS_PAGE = true`）する場合は `requests.php` 内スクリプトとの重複・競合を整理する必要がある。

**M11. ルール適用開始日の扱い**
画面は「今日時点で有効なルール」を表示する。未来日付で保存したルールは、その日まで画面に反映されず、保存し直すと意図せず上書きされ得る。また `rules_effective_date` 設定自体は保存操作で更新されない。

**M12. 期間一括消化（`execute_range`）の仕様差**
同日の重複チェックが無く、`unit_type` と 1日固定が混在。UI が無いため実運用では使われていない。

## 4. 重要度「低」

**L1. `get_summary` の `total_expired` 等、後方互換用の冗長キー**が残っている。
**L2. `README` と本資料で触れていない `test.html`** は空のテストページで機能なし（デプロイ対象に含まれる）。
**L3. 失効処理の条件 `remaining_days > 0`**：残0のまま期限切れとなった付与は `is_expired=0` のまま残る（有効判定は `expiry_date` も併用するので集計は正しい）。
**L4. 日付処理の混在**：判定は `date()`（サーバータイムゾーン）、記録は `current_time()`（WP設定）。タイムゾーン不一致の環境では日付境界がずれ得る。
**L5. N+1 クエリ**：従業員一覧・集計表は社員ごとに7本程度のクエリを実行する。社員数が増えると遅くなる。
**L6. 権限不足の応答が不統一**：`wp_die(-1)` と `wp_send_json_error` が混在。
**L7. `PL_Request::create` の `wpdb->update` のフォーマット指定数が値より少ない**（実害は小さい）。
**L8. 社員コードの結合が文字列**：社員マスタ側の変更・削除に追従しない（孤児データが残り得る）。
**L9. CSV付与インポートの `tenure_months` は取込時の付与日基準**、付与画面は今日基準。履歴の「勤続月数」の意味が揃っていない。
**L10. デプロイに除外設定が無い**ため、ドキュメント類（`docs/`）やテストファイルも本番サーバーへ配置される。
**L11. 自動テスト・ビルド工程が無い**（デプロイは push → FTP のみ）。

## 5. 設計判断として確認できる方針（意図的と思われる点）
- PHP 8 の新構文（match 式等）を避け、WordPress 推奨の後方互換を優先（README 開発メモ）。ただし `fn()`（アロー関数）や `intdiv` は個人管理画面で使用。
- マイグレーションは `dbDelta` ＋必要に応じた `ALTER TABLE`。
- JS は jQuery のみ、外部ライブラリ非依存。
- 「今年」の定義を付与起算に統一（コミット `69f71e2`）、有効期限は「付与日＋N年−1日」に統一（コミット `39b9196`）、期限切れの失効を管理画面ロード時に自動実行（コミット `dc140a2`）。
